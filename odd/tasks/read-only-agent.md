# read-only-agent

Objective: integrate AWS Strands into `backend/app/agents/` behind an explicit read-only tool allowlist, so the agent answers portfolio and market questions, cannot mutate any record, and reports uncertainty instead of inventing data.
Branch: `dev` (work-unit commits land here). Delivery strategy: `ask-on-risk` — the measured size and the decision taken are in L4.
Test runner: `python -m pytest backend/tests -q`.

## Specs

Numbered requirements. `S#` are the acceptance criteria; each task links the specs it satisfies. Exact plan wording and exact API-facing strings are quoted verbatim.

- **S1** — `backend/app/agents/` exists as a package with `config.py`, `tools.py`, `service.py` and `runtime.py`; `backend/pyproject.toml` declares the `strands-agents` dependency and lists `backend.app.agents` in its packages; `.env.example` documents the agent variables. Importing the package must work without `strands` installed.
- **S2** — The tool allowlist is explicit and read-only. Exactly four tools are exposed: `read_portfolio`, `read_valuations`, `read_market_analysis`, `read_history`. No write use case (`record_purchase`, `record_sale`, `delete_transaction`, `add_wishlist_item`, `update_wishlist_target`, `remove_wishlist_item`, `add_bibliography_item`, `delete_bibliography_item`) is exposed as a tool or invoked by the registry, and the package holds no SQL text, no session and no engine handle. The registry is the only invocation surface the model can address; the tools do hold the read use-case objects, so their write methods stay reachable through the ordinary Python object graph, which is not that surface (see L8). This is the plan's "Explícita (leer cartera, valuación, análisis, historial); sin SQL arbitrario ni operaciones de escritura".
- **S3** — A tool outside the allowlist is not invocable: invoking it raises `ToolNotPermittedError` and leaves the database unchanged.
- **S4** — Model and AWS region come from the environment (`AGENT_MODEL_ID`, `AWS_REGION`). A missing or blank value raises `AgentConfigurationError`. No credential is part of the settings object or of the answer.
- **S5** — A provider failure, or Strands being unavailable, returns an explicit uncertainty answer with status `unavailable` and no invented price or signal. This is the plan's "fallo de proveedor → respuesta de incertidumbre sin inventar precios".
- **S6** — The Strands import is lazy: only `runtime.py` imports it, inside the factory, so the package imports and every tool works with Strands absent, and asking then fails with a typed error rather than an import-time crash. This is the plan's "Dependencia pesada de Strands (aislar import lazy)".
- **S7** — Scenarios covered: `Read-only analysis` (Analyze a portfolio; Request an unsupported action) and `Tool and credential boundaries` (Tool access is limited; Provider failure).
- **S8** — Scope decision: 6.1 adds no HTTP endpoint. `design.md` lists no agent route among the `/api/v1/` contracts and Coolify access control is still an open question there, so the integration point is a factory that builds the service from the application's read-only use cases and is exercised directly by tests. See L3.
- **S9** — No regression: `python -m pytest backend/tests -q` stays green, no existing endpoint behavior changes, and no test performs real network access.

The plan's allowlist names four reads — portfolio, valuation, analysis, history — so the resource use cases (wishlist, bibliography) stay out and are not injected into the tools at all, rather than being injected and left unused.
- **L3** — Two scope decisions logged because they keep an unproven premise out of the code. First, no HTTP endpoint: `apply-spec.md` makes the route conditional ("endpoint de análisis del agente si corresponde según `design.md`"), `design.md` lists no agent route among its `/api/v1/` contracts, and the mechanism that will protect the single-user deployment is an explicit open question there. Exposing a model-backed endpoint before that question is answered would be the opposite of a read-only boundary. The integration point is therefore a factory over the existing read-only use cases, exercised by tests, and it can be given a route in one small change once the access-control question is resolved. Second, no keyword-based intent detection for "buy, sell, delete, or alter": matching mutation verbs in free text cannot separate a request to mutate from a legitimate read-only question such as whether a position should be bought, so it would refuse valid analysis while proving nothing about safety. The real guarantee is structural — the allowlist contains no mutating tool and no write use case is reachable — and the system prompt routes an explicit mutation request to a confirmation instead. See S2 and S3.
