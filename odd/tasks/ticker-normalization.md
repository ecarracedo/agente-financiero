# ticker-normalization

Objective: make every ticker entering the API normalized and validated in one canonical place, and fix every defect found while doing it, so no ticker debt survives into Phase 6.
Branch: `dev` (work-unit commits land here). Delivery strategy: `ask-on-risk` — the running authored-line count starts at ~728 from `review-debt-cleanup`; this feature is expected to exceed the ~400 heuristic, so delivery slicing is raised with the user rather than applied silently.
Test runners: backend `python -m pytest backend/tests -q`; frontend `cd frontend && npm test`.

## Specs

Numbered requirements. `S#` are the acceptance criteria; each task links the specs it satisfies. Exact user wording and exact API-facing strings are quoted verbatim.

- **S1** — One canonical normalization helper exists at `backend/app/domain/tickers.py` with `MAX_TICKER_LENGTH = 32` and `normalize_ticker(raw)`. It strips and upper-cases, raises `ValueError("ticker is required")` when the normalized value is empty, and raises `ValueError("ticker must be at most 32 characters")` when it is longer than `MAX_TICKER_LENGTH`. Every site that turns a caller-supplied ticker into a stored or validated symbol delegates to it. Repository lookup paths keep their defensive `strip().upper()` and are deliberately exempt: their contract is to report absence with `None`/`False`, so raising on a symbol that merely does not exist would be wrong. See L8 for why the wider refactor was rejected. The two layers deliberately measure different strings: the declared contract bound (`Path`, `Query` and `Field`) rejects an over-long RAW string before the route body runs, with FastAPI's own `string_too_long` message, exactly as the body and query parameters already did before this change; `normalize_ticker` then validates the NORMALIZED symbol for any caller that reaches it, with the message above. A padded symbol whose normalized form fits while its raw string does not is therefore rejected by the contract layer. That is accepted, documented behavior rather than a defect, because removing the declared bound would either weaken the published schema or make the path parameters inconsistent with the body and query parameters. See L11.
- **S2** — Every path-parameter ticker endpoint rejects an empty, whitespace-only, or over-long ticker with **422** before touching any use case, market provider, or repository. The affected endpoints: `GET /analysis/{ticker}`, `PUT /portfolio/{ticker}/alert`, `POST /portfolio/{ticker}/alert/check`, `PUT /wishlist/{ticker}/target`, `DELETE /wishlist/{ticker}`, `PUT /wishlist/{ticker}/alert`, `POST /wishlist/{ticker}/alert/check`.
- **S3** — Body tickers are normalized and validated by the request contract: `POST /wishlist` and `POST /transactions` reject a whitespace-only or over-long ticker with **422**, and accept surrounding whitespace by normalizing it (`" aapl "` becomes `AAPL`).
- **S4** — No request can create a wishlist row whose ticker is empty or longer than `MAX_TICKER_LENGTH`. In particular a whitespace-only ticker on `POST /wishlist` and on `PUT /wishlist/{ticker}/alert` leaves the database unchanged and returns 422. The wishlist persistence path validates even when it is reached from another use case, so `configure_wishlist_alert` cannot create an empty row either.
- **S5** — `GET /analysis/{ticker}` with a whitespace-only ticker returns **422**, not 500. The unhandled `ValueError` currently escaping to the framework is gone.
- **S6** — The alert check endpoints return **422** for an invalid ticker instead of 503 `market price unavailable`. An invalid ticker is a client error and must not be reported as an unavailable upstream service.
- **S7** — The `ticker` query parameter of `GET /transactions` follows the same rule as every other ticker input: normalized, empty/whitespace-only/over-long rejected with **422**.
- **S8** — The domain keeps a single source of truth: `domain/portfolio.py`, `domain/analysis.py` and `application/analytics.py` call `normalize_ticker` instead of duplicating the normalization. Existing behavior is preserved: an over-long ticker that used to be silently truncated by the database column must no longer be accepted, and every currently-passing behavior that does not involve an invalid ticker stays identical.
- **S9** — The OpenAPI snapshot `frontend/openapi.json` and the generated `frontend/src/api/types.ts` are regenerated for the changed operation metadata, and both drift guards (`npm run check:api-drift`, `backend/tests/test_openapi_snapshot.py`) pass.
- **S10** — The frontend test runner rejects a committed `.only` explicitly rather than relying on the tool's default, closing review finding `R3-ci-no-forbid-only`.
- **S11** — `configure_wishlist_alert` rejects an invalid ticker (blank or over-long) by raising `ValueError` and persists nothing, so the auto-add path cannot create an unusable wishlist row, while its auto-add behavior for a valid ticker is unchanged. This closes review finding `R3-no-invalid-ticker-alert-test`. See L9 for why the `RuntimeError` invariant branch was not covered by a stub repository instead.
- **S12** — No regression: every existing endpoint behavior that does not involve an invalid ticker keeps its previous response. Existing tests keep passing without being weakened.

## Log

- **L1** — User request, verbatim: "Normalizemos todos antes de Fase 6, si se encuentra un error en el camino arreglemoslos. No quiero deuda tecnica antes de empezar Fase 6". It answers the open decision from the `review-debt-cleanup` review: validate and normalize tickers rather than pin the current permissive behavior. The two remaining informational findings of that review (`R3-ci-no-forbid-only`, `R3-no-invalid-ticker-alert-test`) are folded in so no advisory survives into Phase 6.
- **L2** — Entry points and current behavior mapped by reading `api/routes.py`, `api/schemas.py`, `application/alerts.py`, `application/resources.py`, `domain/portfolio.py`, `domain/analysis.py`, `application/analytics.py`, `adapters/persistence/repositories.py`, `adapters/persistence/models.py` and the migration adapter. Confirmed defects: a whitespace-only ticker creates an empty wishlist row through `POST /wishlist` and through `PUT /wishlist/{ticker}/alert`; `GET /analysis/{ticker}` returns 500 for a whitespace-only ticker because the domain `ValueError` is unhandled there; the alert check endpoints return 503 `market price unavailable` for an invalid ticker; and every path parameter accepts an over-long ticker that SQLite stores because it ignores the declared `String(32)`.
- **L3** — Root cause is structural, not a missing bound: path parameters are declared as bare `str` with no validation, and the wishlist path bypasses the domain entirely (`add_wishlist_item` goes straight to the repository) while portfolio positions pass through `PortfolioPosition.__post_init__`. Fixing only the length bound would leave the empty-row defect and the 500s in place.
- **L4** — Design decision: validation is two-layered. The API boundary rejects invalid input with 422 so the contract is explicit and documented in OpenAPI, and the domain helper is the single source of truth so a path that bypasses the API still cannot persist an invalid ticker. The repository keeps its defensive normalization because the migration importer calls adapters directly with raw legacy values.
- **L5** — Migration-safety check before changing the repository: the legacy importer writes `WishlistRecord` directly through its own `_upsert` and never calls `SqlAlchemyResourceRepository.add_wishlist_item`, and `_validate_wishlist_items` already rejects rows with a missing ticker. Adding the write guard to that repository method therefore cannot make an existing migration fail.
- **L6** — Boundary implementation choice: the path and query bounds are declared with `Annotated[str, Path(...)]` / `Annotated[str, Query(...)]` aliases. This keeps every route signature in its original parameter order (no unrelated churn), documents the bounds in OpenAPI, and leaves `_canonical_ticker` as the single place that normalizes and turns an invalid symbol into 422. `TransactionRequest.ticker` deliberately gained no extra validator: `POST /transactions` already rejected a whitespace-only ticker with 422 through the domain, so the only change there is the message, which now names the ticker ("ticker is required") instead of the vaguer combined "ticker, broker, and category are required". That is a same-status message correction, not a contract change.
- **L7** — T4 evidence, measured rather than assumed. A throwaway probe test with a top-level `it.only` whose sibling asserted `1 === 2` was run twice and then deleted: plain `npx vitest run` reported `1 passed | 1 skipped`, while `CI=true npx vitest run` failed with `Error: [Vitest] Unexpected .only modifier. Remove it or pass --allowOnly argument to bypass this error`. So CI already blocks a committed `.only`; the finding was that this rested on an implicit default. The config now pins `allowOnly: !process.env.CI`, which preserves the local debugging workflow and makes the CI rule explicit.
- **L8** — Scope decision on S1, logged because it narrows the original spec. The first draft required that no site re-implement `strip().upper()` for tickers, which would have meant rewriting thirteen repository call sites. Those sites are lookups and key-based updates whose contract is to report absence with `None`/`False`; converting them to a raising call would change behavior that nobody asked to change, for a stylistic gain. The smallest coherent change was preferred: the validating helper is the single source of truth for the canonical form and is used everywhere a caller-supplied ticker becomes a stored or validated symbol, and the exempt lookup paths are documented in S1 rather than silently left inconsistent.
- **L9** — T5 scope decision: the finding `R3-no-invalid-ticker-alert-test` concerns the auto-add path in `configure_wishlist_alert`, so the test covers that path (blank and over-long ticker, `ValueError`, wishlist still empty) instead of the `RuntimeError` invariant branch originally sketched in S11. Reaching that branch requires a stub repository that reports the row as missing immediately after writing it; it is a defensive assertion against a broken adapter, not part of the review finding. Its baseline RED was demonstrated one layer up: `PUT /wishlist/{blank}/alert` returned 200 and persisted an empty-ticker row before this change.
- **L10** — T6 evidence. The OpenAPI drift was inspected before regeneration and was exactly seven hunks of `minLength: 1` plus `maxLength: 32` on the seven ticker path parameters: fourteen added lines and zero removed. The query parameter did not drift because it already declared those bounds. Regeneration reproduced the file byte-identically apart from those fourteen lines, and `frontend/src/api/types.ts` needed no change because path-parameter bounds do not affect the generated TypeScript. Backend `151 passed`, frontend `15 files / 91 tests`, `npm run lint` clean, `npm run build` clean, `npm run check:api-drift` passed, `backend/tests/test_openapi_snapshot.py` passed.
- **L11** — Independent verification result. All twelve requirements `met`, zero blockers, two advisories, no workspace pollution and no unrelated behavior change. The baseline comparison confirmed every targeted defect and confirmed that ten representative valid-input requests return the same status and body at `a7c34f6` and at `93e218b`; the only same-status difference is the documented `POST /transactions` blank-ticker message in L6. Advisory one: the declared contract bound measures the raw string, so `PUT /wishlist/` with a thirty-character symbol padded out to thirty-eight characters now returns 422 `string_too_long` where the baseline accepted and stored it. Accepted as intentional and written into S1, because the alternative would either remove a pre-existing published bound from the body and query contracts or leave the path parameters measuring differently from them. Advisory two: the over-long path message is FastAPI's `string_too_long` rather than the helper's text; the status is 422 either way and the existing body and query parameters already behaved that way before this change. Neither advisory is change-caused on a realistic input, and neither is being fixed silently: both are recorded here and reported to the user.
